# 飞鹊组件使用经验和规范

> 适用范围：所有基于飞鹊组件库的 MIC（Made-in-China.com）Web 端页面
> 持续更新，以本文件为准

---

## 零、参考与组件的关系（铁律，最高优先级）

**可以参考任何优秀页面（阿里巴巴、Amazon、独立站等）的布局、信息架构、交互模式，但实现时所有 UI 元素必须用飞鹊 Web 组件库。绝对禁止从参考页面抄样式值。**

### 参考页面提供什么（学）

- 布局思路、模块排列、视觉动线
- 信息层级、内容优先级策略
- 留白节奏、卡片密度、CTA 位置策略
- 交互模式（hover 反馈、滚动加载、筛选逻辑）

### 飞鹊组件库提供什么（用）

- 按钮（`.btn-primary` / `.btn-secondary` 等）、输入框、选择器
- 颜色 token（`#E64545` / `#007DFA` / `#222` / `#555` / `#888`）
- 字号（14px 基准 / 16px 区块标题 / 12px 极少注释）
- 投影（`.shadow-1` / `.shadow-2` / `.shadow-3`）
- 圆角、间距、图标等一切 UI 原子

### 正确心智模型

```
参考页面 = 设计策略（学"为什么这样排"）
飞鹊组件 = 实现工具（用"我们自己的砖"）
```

### 举例

| 场景 | ❌ 错误 | ✅ 正确 |
|------|---------|---------|
| 按钮圆角 | 阿里巴巴用 border-radius:20px，照抄 20px | 学习 CTA 位置策略，用飞鹊 `.btn-primary`（radius:6px） |
| 卡片投影 | 参考页面是 0 2px 8px rgba(0,0,0,0.15)，照抄 | 学习 hover 浮起效果，用飞鹊 `.shadow-2` |
| 字号 | 参考页面正文 13px，照抄 | 学习信息层级划分方式，用飞鹊 14px 基准 + 颜色层级 |
| 颜色 | 参考页面主色 #FF6A00，照抄 | 学习色彩对比策略，用 MIC 主色 #E64545 |

## 一、组件使用规则（死命令）

### 1.1 必须使用飞鹊组件库

做 MIC Web 端页面时，所有 UI 元素必须优先使用飞鹊组件库的组件和 class，禁止自己重新造轮子。

- 组件库 CSS：`飞鹊Web组件库.css`
- 组件示例：`飞鹊Web组件库.html`、`飞鹊按钮规范.html`

### 1.2 组件样式绝对不能修改（最高优先级）

**飞鹊组件的 UI 样式、颜色、描边粗细，任何情况下都不允许擅自修改。**

- ❌ 禁止修改按钮颜色（必须用原色：主红 `#E64545`、蓝 `#007DFA`、黑描边 `#222` 等）
- ❌ 禁止修改描边粗细（组件原值为 1px，不能改为 1.5px / 2px）
- ❌ 禁止自创组件变体（只能用库里已有的 primary / secondary / secondary-blue / secondary-dark 等）
- ✅ 创新样式只能在**组件之外的布局容器层**实现

### 1.3 Figma 组件创建规范

**在 Figma 中创建新组件时，必须遵循以下规则：**

#### 描边标识（死命令，不可跳过）

- Component Set（组件集）整体加 **2px #8A38F5 内描边**，作为组件边界标识
- 组件内部的变体（Component）**不加描边**，保持干净
- ❌ 禁止把标识描边加在每个变体上
- ❌ **禁止给被引用的子组件加紫色描边**——即使它本身是 COMPONENT，只要会被其他组件实例化引用，就不能加。描边会随实例传播到所有引用处，导致内部嵌套的面板/菜单全部出现紫色边框
- 实战案例（2026-04-09 Cascader）：Cascader Menu 子组件加了紫色描边 → 被 Cascader 组件集的 open=yes 变体引用后，每个菜单面板都出现紫色边框

#### 样式绑定（死命令：零硬编码，不可跳过）

**组件中的每一个颜色、每一个文字样式，都必须绑定飞鹊的 Style，绝对禁止硬编码色值。没有例外，包括"看起来不重要"的分割线和背景色。**

##### 文字
- 必须绑定 **Text Style**（如 `body/xl`、`body/base`），不能手动设字号
- 字体必须显式设置 `fontName = Roboto`，不能依赖默认值

##### 颜色（全部绑定，无一遗漏）
- 必须绑定 **Paint Style**，不能手动写色值
- 常见遗漏点（每次都要检查）：

| 容易遗漏的元素 | 硬编码色值 | 应绑定的 Style |
|--------------|-----------|---------------|
| 面板/卡片背景 | `#FFFFFF` | `other/white` 或 `background/background 03` |
| 分割线 | `#E6ECF2` | `dividing line/border` |
| 输入框边框 | `#CED3D9` | `dividing line/button` |
| 灰色背景 | `#F5F7FA` | `background/background 01` |
| 禁用文字 | `#B3B3B3` | `text/disable` |

##### 飞鹊完整 Paint Style 速查

**执行方法**（Figma Plugin API）：
```js
const paintStyles = await figma.getLocalPaintStylesAsync();
const style = paintStyles.find(s => s.name === 'dividing line/border');
await node.setFillStyleIdAsync(style.id);
```

#### 子元素必须用飞鹊组件实例（死命令，零容忍，不可跳过）

**按钮、图标等一切飞鹊组件库里已有的元素，必须通过 `importComponentByKeyAsync` 导入为 Instance（实例），绝对禁止以下任何替代方式：**

| ❌ 禁止 | ✅ 正确 |
|---------|---------|
| 用 Text 节点写 ✕ / → / ● 字符当图标 | `importComponentByKeyAsync('icon=delete 的 key')` |
| 用 `createNodeFromSvg` 手画 SVG 路径当图标 | 同上，导入飞鹊图标组件实例 |
| **用 Frame + 手动设色值/圆角重建按钮** | **`importComponentByKeyAsync('button 的 key')`（零容忍）** |
| 「先占位回头再换成组件」 | **没有回头，第一步就用组件实例** |
| **「手画更快，少几次调用」** | **这就是节省 token 冲动，必须根除** |

**为什么**：手画的路径和飞鹊组件实例看起来可能一样，但实例会跟随组件库更新，手画的不会。而且「先占位回头换」在实际操作中**从来不会换**——每次都忘。

##### ⚠️ 节省 token 冲动 = 此规则最大的敌人（必须根除）

**LLM 在批量创建变体时，会下意识觉得「手动 Frame + 色值更快，少几次工具调用」——这是结构性弱点，不是偶尔犯的错，是每次都会倾向犯的错。**

每次创建包含按钮/图标/勾选框等元素的组件时，强制自检：
1. **停下来问：「这个元素飞鹊组件库里有没有？」**
2. 有 → **必须 import，没有例外。**
3. 觉得"手画更快" → **这就是节省 token 冲动的信号，强制走 import 流程。**

历史翻车记录：
- 2026-04-10 Form 表单：5 个新变体的 20 个按钮全部手动重建，被指出后全部返工
- 2026-04-09 Drawer/Cascader：按钮手动创建，不跟随组件库更新
- **每一次都是同一个原因：节省 token 冲动**

##### 按钮配对规则（死命令）

表单/浮层的确定+取消按钮，必须用同色系配对：

| 按钮 | 变体 | 视觉 | component key |
|------|------|------|---------------|
| 确定（主操作） | `type=primary, color=red` | 红底白字 | `7d10df50be1343101f07d9c37e452262f4582098` |
| 取消/重置（次操作） | `type=secondary, color=red` | 白底 #222 黑边黑字 | `9f607e400a182ec5cecc8ffbebeca428318aff31` |

**"color=red" 指配对色系（跟 primary red 配对），不是按钮本身是红色。secondary red 实际是黑边黑字。**

##### 按钮通栏注意事项

按钮实例设为 `layoutSizingHorizontal = 'FILL'` 后，必须同时设 `primaryAxisAlignItems = 'CENTER'`。飞鹊按钮默认对齐是 MIN，拉通栏后不改对齐，文案就跑到左边。

**执行方法**（Figma Plugin API）：
```js
// 按钮组件集 key: 763190f9f69421d390401bb5eecc289e617c7c72（名称 "botton"，540变体）
// 直接用单变体 key 导入
const submitComp = await figma.importComponentByKeyAsync('7d10df50be1343101f07d9c37e452262f4582098');
const submitInst = submitComp.createInstance();
const resetComp = await figma.importComponentByKeyAsync('9f607e400a182ec5cecc8ffbebeca428318aff31');
const resetInst = resetComp.createInstance();

// 图标
const iconComp = await figma.importComponentByKeyAsync('d3b97c46e495...');
const instance = iconComp.createInstance();
instance.name = 'Close';
instance.resize(16, 16);
parent.appendChild(instance);
```

#### 组件描述（死命令，不可跳过）

**每个 Component Set 和 Component 创建完成后，必须在 description 里写完整描述。不允许只写 `fd_组件名` 就交付。**

描述必须包含以下内容：
1. **fd_ 前缀 + 英文名 + 中文名**（如 `fd_List Item 列表项`）
2. **变体数量和维度**（几个变体、什么属性组合）
3. **结构说明**（内部元素组成：标题/描述/图标/箭头等）
4. **状态样式**（每种 state 的背景色、文字色、具体值）
5. **绑定的 Style 列表**（用了哪些 Paint Style / Text Style）
6. **适用场景**（每个变体适合什么业务场景）
7. **关键设计决策**（为什么用普通箭头不用 big、为什么无圆角等）

示例：
```
fd_List Item 列表项
尺寸：small(36px) / default(44px) / large(64px，含12px描述)
状态：default / hover(#F5F7FA) / selected(#F5F7FA+蓝色文字) / disabled(#B3B3B3)
结构：标题(14px #222) + 描述(12px #888，仅large) + 右箭头(right icon) + 底部分割线
样式绑定：text/title · text/auxiliary · text/disable · primary/supplier · background/background 01 · dividing line/border · body/base · body/lg · footnote/sm
```

**为什么**：描述是组件的"使用说明书"，点击组件右侧面板就能看到。没有描述，其他设计师拿到组件不知道有几种变体、什么场景用哪个、样式绑了什么——等于白做。

#### 变体排版

- 多变体用 **网格排列**（行=尺寸，列=状态），间距 60px，外围 padding 60px
- 变体命名格式：`width=narrow, button=no`（英文小写，逗号+空格分隔）

#### 行分割线技巧（死命令：strokeBottomWeight，禁止子节点）

**表格/列表的行底部分割线，必须用 row FRAME 自身的 `strokeBottomWeight=1`，禁止创建独立的 1px 子 FRAME 充当分割线。**

| | 错误做法 | 正确做法 |
|--|---------|---------|
| 实现方式 | 创建 1px 高度子 FRAME，fillStyleId = dividing line/list | row FRAME 自身设 strokeBottomWeight=1 |
| 结构 | VERTICAL wrapper + content + divider 三层 | 单层 row FRAME，无多余子节点 |
| 行高计算 | content(30) + divider(1) = 31px | content(30) + paddingBottom + stroke inside |

```js
row.strokes = [{ type: 'SOLID', color: C.div }];
row.strokeStyleId = S.divider;   // dividing line/list
row.strokeWeight = 1;
row.strokeAlign = 'INSIDE';
row.strokeTopWeight = 0; row.strokeRightWeight = 0;
row.strokeLeftWeight = 0; row.strokeBottomWeight = 1;
```

注意：`strokeStyleId` 读取时返回 `figma.mixed`（Symbol），四边独立时正常现象，verify.js 有 try/catch 保护。

（实战案例：2026-04-14 ranking-list）

#### 自适应布局（死命令，不可跳过）

**做任何 Figma 稿子（组件、页面、示例），都必须强制使用 Auto Layout 自适应布局。禁止用手动定位（layoutMode='NONE' + 固定坐标）。**

##### 为什么

手动定位在改尺寸时不会自动调整——改了高度，底部的 Footer/Divider 还停在原位，必须手动一个一个挪。Auto Layout 下改尺寸，所有子元素自动重排，零手动调整。

##### 关键 sizing 规则

| 元素角色 | layoutSizingVertical | layoutSizingHorizontal |
|---------|---------------------|----------------------|
| 固定高度区（Header/Footer） | `FIXED` | `FILL` |
| 分割线 | 自动（1px 高） | `FILL` |
| 内容区（Body） | **`FILL`**（撑满剩余空间） | `FILL` |
| 面板本身 | `FIXED`（固定总高） | `FIXED`（固定总宽） |

**`FILL` 是关键**：Body 设为 `FILL` 后，无论面板总高怎么变，Header 和 Footer 固定不动，Body 自动伸缩吃掉中间空间。

##### 实战案例（2026-04-09 Drawer 极限值展示）

```
❌ 错误：改高度 560→960 后，用手动坐标补偿 Footer 位置
  → Footer Divider 和 Footer 位置错乱，没跟着高度变化

✅ 正确：全部用 Auto Layout
  → Header FIXED + Body FILL + Footer FIXED
  → 改高度后 Footer 自动贴底，零手动调整
```

### 1.4 组件内部字重凌驾一切

**组件库 CSS 定义的 `font-weight` 是最高优先级，绝对不能用外部样式覆盖。**

组件用什么字重就是什么字重，不受下方"字重规则"约束。

### 1.5 使用 Figma 组件实例时：直接改内部文字，禁止外挂文案（死命令）

**飞鹊组件库里的带文字组件（checkbox、button、tab、badge、brand logo 等）内部已经包含 TEXT 图层。需要改变显示文案时，必须直接覆写实例内部的 TEXT 节点，绝对不允许把"组件实例 + 另一个独立 TEXT 节点"拼在一起当"带文字的组件"。**

#### 为什么

- 一句文案存在两处来源（组件内部 + 外部 TEXT）→ 改一处漏一处
- 组件自带文字的样式（字号、字重、颜色、行高、间距）都被绑定在库里，外挂 TEXT 需要手动对齐，必然差一点点
- 组件有 hover/active/disabled 状态时，外挂 TEXT 无法同步变化
- 代码可读性差：看起来像"组件 + label"，实际是重复文字或文字叠文字
- Figma 里 swap variant 时内部文字保留，外挂 TEXT 变成孤儿

#### 正确做法（use_figma 代码示例）

```js
// ✅ 正确：override 内部 TEXT
const cb = kCheckbox.createInstance();
parent.appendChild(cb);
const t = cb.findOne(n => n.type === 'TEXT');
if (t) {
  await figma.loadFontAsync(t.fontName);
  t.visible = true;              // 如果之前被隐藏过要 un-hide
  t.characters = 'Select all';   // 直接改组件内部文字
}
```

```js
// ❌ 错误：组件 + 外挂 TEXT
const cb = kCheckbox.createInstance();
parent.appendChild(cb);
const external = mkText('Select all', 14, 'Regular', COLOR_T1, 22);
parent.appendChild(external);  // ← 多余，会和 cb 内部文字重复
```

#### 常见踩坑场景

| 组件 | 内部已有文字 | 常见错误 |
|------|------------|---------|
| `checkbox` 带 label 变体 | `已选` / `Select all` / `未选` | 外面再加 `Select all` TEXT → 显示 "☑ 已选 Select all" |
| `botton`（飞鹊按钮）| `Button` / `Submit` 等占位 | 没 override 导致所有按钮都显示 "Button" |
| `tab item` | tab 标签文本 | 外面拼 `All (5/20)` TEXT → 重复 |
| `brand logo` | 品牌文字本身 | 外面加 "LeadingFactory" TEXT → 显示两次 |

#### Variant 选择也要先确认「内部有没有文字」

组件同一个 set 里会有「带 label（width 48）」和「icon only（width 16）」两种变体。读取 metadata 时看 `width`：

- 48×22 → 内部有文字层，**直接 override** 内部文字
- 16×16 / 14×14 → 纯图标无文字层，这种才允许外挂 TEXT

用错变体（把 48 的 label 变体当 icon 用 → 外面再加 TEXT）会导致重复显示 bug。

#### 实战案例（2026-04-19 PC 端对比工具）

第一版产品卡 Select 覆盖层用 `kCbUnselected`（以为是 16×16 icon）+ 外挂 `mkText("Select")`。结果发现该变体其实是 48×22 带 label 的版本，内部已有 `未选` / `Select all` 文字，导致页面显示 `☑ Select all Select`（重复）。

正确改法：用 `inst.findOne(n=>n.type==='TEXT')` 定位内部 TEXT，`characters = 'Select'`，并删除外挂 mkText。

#### 实战案例（2026-04-20 文件管理表格列合并）

飞鹊 checkbox 组件**所有变体都内置 `可选` TEXT 占位**（visible=false 默认隐藏，字号 14px Roboto）。表格"选择 + 文件名"两列常见错误做法是：checkbox 一列 + 独立文件名 TEXT 一列。正确做法：

```js
// ✅ 直接用 checkbox 内部 TEXT 作为文件名 label
const innerT = cbInst.findOne(n => n.type === 'TEXT');
await figma.loadFontAsync(innerT.fontName);
innerT.visible = true;          // 取消默认隐藏
innerT.characters = '公司营业执照2024.pdf';
// ❌ 禁止外挂：td.appendChild(mkText('公司营业执照2024.pdf'))
```

这样能：① 合并原本的两列为一列（节省 40px 宽度）② 文件名点击直接作用于 checkbox 勾选区域 ③ 保持组件级联更新

### 1.6 描边的层次逻辑（死命令，描边一次讲清）

**描边是层级设计决策，不是防御性修补。看到 "sides 有 weight 但 strokes 空" 时，第一反应永远是"这一层真需要描边吗？"——绝大多数情况下该**清零**而不是补色。**

#### 1.6.1 先建立层次逻辑（必读）

页面有层次：`page > section > card > row > cell > 元素内部`。**只有极少数层级天生需要描边**：

| 层级 | 天然需要描边？ | 说明 |
|------|------------|------|
| page / main / content-wrap | ❌ 从不 | 页面级没边界 |
| header / nav / tabs / filter bar | ❌ 从不 | 组件库内部自带视觉划分 |
| card 容器（AI Insight / 底栏 / banner 等）| ❌ 从不 | 用背景色 / 阴影 / 圆角划分 |
| section 标签行（"Product Information" 这种）| ✅ 下边 1px | 与下面内容的分隔 |
| 表格 row | ✅ 下边 1px（除末行）| 横向分隔行 |
| 表格 cell（非第一列 label）| ✅ 左边 1px | 纵向分隔列 |
| 第一列 label cell | ❌ 四边全零 | row 的下边已接管水平分隔 |
| 功能性胶囊/按钮（select pill、chat btn、arrow btn 等）| ✅ 四边 1px | 形态本身需要 outline |
| 其他容器/wrapper / Frame 260 这种 group | ❌ 从不 | 纯排版用，无视觉语义 |

**心智模型**："这个元素有独立的视觉盒子身份吗？" 有 → 可能需要描边；没有 → 清零。

#### 1.6.2 Figma 默认 strokeWeight 陷阱（最容易踩的坑）

**Figma 新建 FRAME 时 4 边 `strokeWeight` 默认都是 1**，但 `strokes` 数组初始为空 → 看起来没描边。**所以每个不要描边的 FRAME 建完必须立即 `clearSides()`**：

```js
function clearSides(n){
  n.strokeTopWeight = 0;
  n.strokeBottomWeight = 0;
  n.strokeLeftWeight = 0;
  n.strokeRightWeight = 0;
}

const cell = figma.createFrame();
cell.name = 'cell-label/xxx';
clearSides(cell);           // ← 必须立刻清
cell.fills = [];
```

否则后续任何给它加色的操作（复制自带色 frame、ghost border 扫描、setFill 误加）都会把 4 边全显示出来。

#### 1.6.3 描边 = strokes + weight 必须配对

一条边**可见**需要满足两个条件：`strokes[]` 里有颜色 **AND** 该边 `strokeXWeight > 0`。缺一：

- `strokes=[]` + `weight>0` → **ghost border**（占位但看不见）
- `strokes=[{...}]` + `weight=0` → 颜色白设
- `resize / combineAsVariants / 手动 group` 可能清掉 `strokes` 只留 weight

**但：发现 ghost border 不等于要补色！先判断"这一层本来该有边吗"，不该有就 clearSides。**

#### 1.6.4 表格描边层级：seam 只能 1px

表格里 row 交界、cell 交界、section 交界处 **只允许 1 条 1px**。不能相邻两个元素各给一条叠成 2px。

**一套策略到底：row 管水平分隔 + cell 管垂直分隔**

- row（所有数据行 + section 标签行）: `strokeBottomWeight=1`，其余三边 =0（末行例外 =0）
- 第一列 label cell: **四边全 0**（row 的底边接管水平分隔）
- 其他列 cell: `strokeLeftWeight=1`，其余三边 =0
- section 标签行: **充满单行**（一个 row + paddingLeft 缩进 + 直接放 TEXT），**禁止切成 label cell + 空 cell 布局**；只用 `strokeBottomWeight=1`，**绝不加 `strokeTopWeight`**（上一行的 bottom 已经接管交界）
- 末行（整个表格的最后一行）: `strokeBottomWeight=0`

反例（都踩过）：
```
row A { bottom=1 }  +  row B { top=1 }        → 叠 2px
cell-label { 4 边默认 1 }  +  cell-value { left=1 }   → 叠 2px
row { bottom=1 }  +  cell inside { bottom=1 }       → 叠 2px
section 标签切成 [label cell] + [empty cell × 5]     → 切段感，失去 section 统一性
```

#### 1.6.5 写代码顺序

```js
// ✅ 步骤：先 strokes，再 sides
n.strokes = [{ type:'SOLID', color: COLOR_BORDER }];
await n.setStrokeStyleIdAsync(PS_BORDER.id);   // 绑定 dividing line/border
n.strokeTopWeight = 0;
n.strokeBottomWeight = 1;  // 要哪边就开哪边
n.strokeLeftWeight = 0;
n.strokeRightWeight = 0;
```

#### 1.6.6 收尾检查清单

页面交付前必做：

1. **扫 ghost border**（有 weight 无 strokes）：不是全补色！先判断层级该不该有边，不该就 clearSides
2. **扫未清零默认边**（新建 FRAME 遗忘 clearSides）：批量 clearSides 掉所有不需要描边的 wrapper/容器
3. **扫 instance 内部 stroke override**：我不该改的就不该改；误改了就 `setStrokeStyleIdAsync('')` 解绑 + 清 strokes + clearSides
4. **扫表格 seam**：确保每条交界只有一方有 1px，不是两方

#### 1.6.7 实战案例链（2026-04-20 PC 端对比工具，三连坑）

1. **坑 1**：Frame 260（用户手动 group 的 Product Info 容器）`sides=1/1/1/1` + `strokes=[]` → section 顶部描边消失
2. **坑 2 误修**：扫全页 148 处 ghost border 全部补色 `dividing line/border` → **把 Header 实例内部、compare-products-bar、AI Insight、底栏等所有无关容器都加上了描边，视觉噪音爆炸**
3. **坑 3 表格 seam**：配合默认 4 边 weight=1 在 cell-label / cell-select-all 上激活 → 174 处变成全框边格子
4. **最终正解**：
   - 回滚：非表格元素 112 处 + instance 内部 425 处 stroke 全部解绑清零
   - 白名单保留描边：只在 `row/*`、`product-card`、`cell-value`、`select-pill`、`select-all-pill`、`btn-chat-now`、`btn-arrow-right` 这些**真需要边界的层级**保留
   - Frame 260 清零（wrapper 没视觉语义）
   - section 标签行重建为"充满单行 + 下边 1px"，不切 cell

**核心教训**：看到 ghost border 不要条件反射地补色，先问"这一层本来该有描边吗"。大多数 Figma 默认残留 weight 的 FRAME，正确操作是 clearSides 而不是加色。

#### 1.6.8 绝不触碰 INSTANCE 内部 stroke（否则组件原生描边被清）

**批量遍历节点改 stroke 时，必须 `isInsideInstance(n) → skip`**。飞鹊组件（checkbox / radio / button / tab 等）内部的方框、勾、分隔线等全都是用 vector 的 stroke 绘制，一旦被误清组件就"裸奔"了。

```js
function isInsideInstance(n){
  let p = n.parent;
  while (p){ if (p.type === 'INSTANCE') return true; p = p.parent; }
  return false;
}

root.findAll(n => {
  if (isInsideInstance(n)) return false;  // ← 必须 skip
  // 只对非 instance 节点操作 stroke
  // ...
});
```

**误改后的修复**：对被清的 INSTANCE 实例调用 `inst.resetOverrides()` 一键恢复库默认，然后重新应用你想要的 override（text / layout positioning / x, y）。比逐个猜测原值快得多。

实战案例：2026-04-20 清 ghost border 时把 MIC Header 实例内 148 处 + 后续 425 处 instance descendant 的 stroke 清零；pinned-top-bar 里 6 个 checkbox 内部方框也被一起抹掉。修复：`inst.resetOverrides()` 6 次，再重设 `characters` 和 `x/y`。

### 1.7 字体只能用飞鹊组件里的 Roboto（死命令，无例外）

**在 Figma 中创建任何文字、修改任何文字时，字体必须是 Roboto，而且必须是飞鹊组件库里已经加载的 Roboto（Regular / Medium / Bold）。禁止以任何理由替换为其他字体。**

#### 铁律

- ❌ 禁止用 PingFang SC / Noto Sans SC / Source Han Sans / 系统默认字体 替代 Roboto
- ❌ 禁止因为"Roboto 显示中文缺字形 / 豆腐块"就擅自切换到支持中文的字体
- ❌ 禁止从 Figma 外部加载新字体文件再用
- ❌ 禁止中英文"混搭"——同一文案一半 Roboto 一半 PingFang
- ✅ 只能调用飞鹊组件库里已声明的 Roboto（Text Style 里的 family 就是 Roboto）

#### 为什么

- 飞鹊所有 Text Style（`body/base`、`body/lg`、`title/xl` 等）全部绑定 Roboto。一旦某个文本换成别的字体，字号/行高/字重/字距全部会错位——字号对，但视觉完全崩坏
- Roboto 对中文"无法显示"是 **Figma 字形缺失的展示问题，不是设计规范问题**。规范定的就是 Roboto，中文渲染由浏览器系统字体 fallback 兜底（body 已经配置系统字体栈），Figma 里的"豆腐块"不影响最终交付
- 只要允许"这一次换一下"，后续组件一致性瓦解，返工成本远大于当下的"方便"

#### 正确做法（use_figma 代码）

```js
// ✅ 必须用 Roboto，加载飞鹊用到的 3 个 style
await figma.loadFontAsync({ family: 'Roboto', style: 'Regular' });
await figma.loadFontAsync({ family: 'Roboto', style: 'Medium' });
await figma.loadFontAsync({ family: 'Roboto', style: 'Bold' });

const t = figma.createText();
t.fontName = { family: 'Roboto', style: 'Regular' };
t.characters = '中文文案也用 Roboto';  // Figma 里显示成豆腐块没关系
```

```js
// ❌ 严禁：为了让中文"看起来正常"换字体
text.fontName = { family: 'PingFang SC', style: 'Regular' };  // 错
text.fontName = { family: 'Noto Sans SC', style: 'Regular' }; // 错
text.fontName = { family: 'Inter', style: 'Regular' };        // 错
```

#### 常见翻车场景

| 场景 | ❌ 错误反应 | ✅ 正确反应 |
|------|-----------|-----------|
| Figma 里中文显示豆腐块 | 换成 PingFang SC | 保持 Roboto，忽略 Figma 显示问题 |
| `loadFontAsync('Roboto')` 报"字体未加载" | 换别的字体 | 让用户在 Figma 本地安装 Roboto |
| 组件里原本是 Roboto，新增文字也得是 Roboto | 用 "本地有的字体" 代替 | 显式 `fontName = { family:'Roboto', style:... }` |
| 设计师截图里中文很清楚 | 以为规范允许中文字体 | 那是浏览器渲染，Figma 规范仍是 Roboto |

### 1.8 Shadow 投射区域必须留空间（Figma z-order 陷阱）

**在 Figma auto-layout 里，前一个子节点的 DROP_SHADOW 投射到下一个子节点区域时，会被后者的 fill 覆盖（因为后者后渲染）。必须在两个子节点之间留 padding/itemSpacing 让 shadow 有"落脚地"。**

#### 触发场景

- Header（带下投影） → 紧贴 content wrapper（带白底）→ shadow 看不见
- Card A（带投影） → itemSpacing=0 → Card B（白底）→ A 的下投影被 B 盖住

#### 原理

Figma 渲染顺序：
1. 父 P 画 fill
2. 子 A 画 fill → 画 effects（shadow）→ 画 A 的子孙
3. 子 B 画 fill → 画 effects → ...

A 的 shadow 落在 **A 之外的 P 背景上**（P 此时已画好）。但 B 是在 A 之后渲染的，B 的 fill **覆盖** B 自己 bounds 内的所有像素 — 包括 A 投射到 B 区域的 shadow。

**B 挨着 A 的上边就会把 A 向下的 shadow 吃掉。**

#### 正确做法

1. **在投影节点下方预留 padding 或 itemSpacing**
   ```js
   content.paddingTop = 16;         // 给上面 header 的 shadow 留空间
   // 或
   content.itemSpacing = 16;        // 每个兄弟之间留空间
   ```
2. **父级 clipsContent 保持 false**（让 shadow 能延伸）
3. **父级 fill 用浅灰/有颜色**（shadow on 白底几乎不可见）

#### 实战案例（2026-04-20 PC 端对比工具 header 投影）

问题：MIC Header 自带 drop shadow（y=3, radius=5, spread=-3, alpha 0.12），但页面看不见。
原因：
- mainFrame fill 曾是白色 → shadow 对比度几乎为零
- content（content-wrap 的子）paddingTop=0，itemSpacing=16 只作用于 siblings，**第一个 child 紧贴 header**
- card/compare-unified 带白底从 y=128 开始 → 盖住 header 在 y=128+ 区域的 shadow

修复：
1. mainFrame fill 改为 `#F5F7FA`（页面灰底，shadow 有对比）
2. mainFrame / content-wrap / content 全部 `clipsContent=false`
3. **content.paddingTop = 16**（核心修复：给 header shadow 留 16px 落地区）

## 二、字重规则

### 2.1 bold 只用于一级信息

**bold（font-weight: 700）只给页面中「最重要的一级信息」，其余一律 regular（400）。**

需要自行判断什么是一级信息，不是机械地"只有标题才能 bold"。

| 允许 bold ✅ | 禁止 bold ❌ |
|---|---|
| 页面标题 h1（商品名、页面名） | 按钮文字 |
| 区块标题 h2 / h3 | 标签 / badge 文字 |
| **价格数字**（产品详情页核心决策信息） | 正文段落 |
| 其他经判断确为一级的信息（通常每页 1–2 处） | 统计数字（订单量、评分等） |
| | 表单标签、输入框内容 |
| | Supplier 名称、导航文字 |
| | 辅助说明、参数值 |

**判断标准**：这个信息是否是当前页/区块用户最需要第一眼看到的内容？一个区块里通常只有 1 处。

### 2.2 必须的 CSS 重置

```css
/* 防止 strong/b 标签意外加粗 */
strong, b { font-weight: 400; }

/* 表单元素不继承 body 字重，需显式声明 */
input, button, select, textarea { font-weight: 400; font-family: inherit; }

/* 覆盖组件库 Roboto 字体声明，继承 body 系统字体 */
.btn, .ss, .rd-label, .inp-num-f input, .inp-num-no input { font-family: inherit; }
```

### 2.3 本地字体陷阱

Figma 本地只安装字体的 Bold 字重（Inter、Roboto 等），导致浏览器即使写了 `font-weight: 400` 也渲染为 Bold。

**解决方案**：body 使用系统字体栈，不使用任何需要安装的命名字体：

```css
body {
  font-family: -apple-system, BlinkMacSystemFont, 'PingFang SC', 'Helvetica Neue', Arial, sans-serif;
  font-weight: 400;
}
```

> 注意：国内无法访问 Google Fonts，禁止添加 Google Fonts `<link>`。

### 5.3 浮层组件按钮搭配规则

**Drawer / Dialog 等浮层组件的确定+取消按钮，必须使用同色系搭配，不能用灰色中性按钮做取消。**

| 按钮 | 组件变体 | 视觉 |
|------|---------|------|
| 确定（主操作） | `type=primary, color=red` | 红底白字（强调） |

## 六、间距规范（死命令，水平和垂直规则不同）

### 6.1 水平间距（padding-left/right、水平 gap）：严格 7 个 token

| token | 值 | 使用场景 |
|-------|------|---------|
| **xxs** | 4px | icon 内间距 · 紧凑元素间隙 · 标签内 padding |
| **xs** | 8px | 组件内 padding · 相关元素间距 |
| **s** | 12px | 卡片内 padding · 表单字段间距 |
| **m** | 16px | 区块内 padding · 模块内部间距 |
| **l** | 24px | 区块间距 · 卡片间距 |
| **xl** | 32px | 大区块间距 · 页面区域分隔 |
| **2xl** | 48px | 页面级间距 · 首屏到内容区 |

### 6.2 垂直间距（padding-top/bottom、垂直 gap）：4px 网格，灵活扩展

推荐优先用上面 7 个 token，不够时允许所有 **4px 倍数**值（20/28/36/40 等）。

常用扩展值：
- **20px** — 区块内分组间距 · 响应式断点常用
- **28px** — 大分组间距 · 页面段落分隔
- **40px** — 页面区域分隔 · 大模块留白

**禁止**：非 4px 倍数值（5/10/15/25/30）

### 6.3 为什么水平严格、垂直灵活

- 水平方向：组件内部结构统一，7 个 token 足够
- 垂直方向：页面层级更复杂（表单项/段落/模块/section/页面），7 个值不够

### 6.4 选择原则

- 间距从小到大 = 关系从近到远
- 同级元素用**相同间距**，不同层级用**不同间距**拉开距离
- **不为了塞内容压缩间距**，宽松的间距本身就是设计质感

Figma 变量集合：`spacing`（绑定 GAP + WIDTH_HEIGHT scope）

## 七、视觉层级原则（逻辑主次，死命令）

> 页面不能"平"。每个区块都必须有一个最重要的信息，其余信息按重要程度递减。没有层级就是没有设计。

### 7.1 层级建立的三个工具（按优先级）

| 工具 | 用法 | 禁忌 |
|------|------|------|
| **颜色深浅** | `#222`（主） → `#555`（次） → `#888`（辅） | 不靠多种颜色区分，靠明度差 |
| **字号大小** | 关键信息可放大（价格 32–36px），其余保持 14px | 不靠缩小字号来降权，用颜色退后代替 |
| **字重** | bold 只给一级信息（每页 1–2 处） | 不滥用 bold，加粗过多等于没有加粗 |

**不需要额外装饰**：用好以上三个工具，层级已经足够清晰。再叠加色块、线条、投影，是信心不足的表现，不是设计能力的体现。

### 7.2 产品详情页层级参考（实战模型）

```
一级（最重要，用户决策核心）
  → 价格：36px bold #222，数字本身就是锚点
  → CTA 按钮：btn-primary，尺寸最大

二级（辅助决策，需快速扫描）
  → 产品标题：20px bold #222
  → 核心参数（MOQ / Lead Time）：14px #222 label + #555 value

三级（信息补充，不影响决策）
  → 认证 / Trust chip：14px #555 或 brand logo
  → 描述段落：14px #555

四级（几乎不看，可选展示）
  → 辅助注释：14px #888
  → 图片计数 1/4：12px #888
```

**关键原则**：同一页面最多 4 个层级。超过 4 层说明有信息需要删除，而不是需要更多视觉手段来区分。

### 7.3 信息精简原则

**删除低价值信息，比增加视觉手段更有效。**

每个信息出现在页面上，都有认知成本。出现之前先问：

1. 用户在这一步决策需要这个信息吗？
2. 去掉它，主要信息是否更突出？
3. 这个信息是"锦上添花"还是"必须有"？

实战案例（2026-04-15 产品详情页）：删掉 "per piece"（价格单位隐含）、"Views"（虚荣指标）、Port + Payment Terms（低决策价值），页面立刻呼吸感倍增。

### 7.4 空间感是层级的一部分

**宽松的间距本身就是层级信号**——重要区块之间给更多间距，视觉上自然分出段落感。不为塞内容而压缩间距，那样等于抹平了所有层级。

- Trust Signal 放在用户决策点附近（CTA 旁/下方），不要堆在页面底部
- 不同重要性的区块，间距差异要明显（不是 16px vs 20px，而是 16px vs 32px）

### 7.5 "算对了"不等于"做对了"

数据正确和视觉有效是两件事。做任何排版、图表之前，先问：**"用户看到这里，第一秒应该理解什么？"** 答不上来，就不该动手排。工程思维关注"数据准不准"，设计思维关注"看一眼懂不懂"——两者都要对，但设计交付以后者为标准。

## 十、统一性原则（死命令）

> 统一不是约束，是质感。形式感元素越少，页面越干净；同类元素越统一，用户越不需要思考。

### 10.1 核心逻辑：混乱不是丰富

用户使用 B2B 平台是来完成任务的，不是来欣赏设计的。**每一个不一致的地方，用户大脑都会自动寻找意义**——"这张卡更重要？""这个颜色代表什么状态？"——如果这个意义不存在，就是在无谓消耗用户认知资源。

**统一的视觉语言让操作变成肌肉记忆，不统一的视觉语言让每一步都需要重新理解。**

### 10.2 装饰性元素：能省则省

**凡是能用字重、颜色深浅、间距建立的层级，就不要再叠加装饰线、色块等形式感元素。**

- ❌ section 标题前加红竖线（`::before` 色块）→ 字重 bold + 间距已经够了
- ❌ 激活价格段加高亮横线 → 字色 #222 + 字号大已经够了
- ❌ 卡片加渐变色边框/光晕 → `border: 1px solid #E6ECF2` 已经够了

**判断标准**：去掉这个装饰元素，信息层级是否还清晰？如果是，就去掉。装饰元素不传递信息，只增加视觉噪声。

### 10.3 投影：全用或全不用（铁律）

**同一视觉层级的卡片/容器，要么全部加投影，要么全部不加。禁止混用。**

- 同类 aside-card → 全部无投影，靠 border 界定边界
- 同类 section-card → 全部无 hover 投影，靠 border-color 变化反馈
- 飞鹊 `.shadow-1/.shadow-2/.shadow-3` 只用于真正悬浮的层（弹窗/下拉/tooltip），不用于普通内容卡片

实战案例（2026-04-15）：aside 两张卡片，一张有 shadow-1 一张没有，第一眼就被发现——用户以为有意义，但没有。立刻统一去掉。

### 10.4 颜色种类：少即是多

**同一个组件的不同状态（default / hover / selected / active），背景色尽量只用一种，靠文字颜色、图标状态、边框做区分。**

- ❌ 3 种状态用 3 种背景色 → 用户分不清哪个代表什么
- ✅ 统一背景色 `#F5F7FA`，靠勾选框 + 文字颜色区分主题

实战案例（2026-04-09 Cascader）：selected 状态从三色（灰蓝浅灰）统一为单色 `#F5F7FA`，视觉立刻干净。

### 10.5 按钮层级：传达操作权重

**按钮的样式必须准确传达操作的重要程度，不能因为"好看"而升降层级。**

| 层级 | 样式 | 适用 |
|------|------|------|
| 主操作 | `btn-primary`（红底白字） | Send Inquiry、Submit 等核心 CTA |
| 次操作 | `btn-secondary`（白底黑边） | Contact Supplier、Cancel 等次级操作 |
| 工具操作 | `btn-secondary-dark`（灰底灰边） | 筛选、排序、导出等中性工具按钮 |

**`btn-secondary-dark` 视觉接近禁用态，不能用于正常可点击的主要操作。**

### 10.6 交互反馈：同类必须统一

**同一组可交互元素，hover 反馈方式必须一致。**

- 同一排卡片：全部用 border-color 加深，不用一张有位移一张没有
- 同一排按钮：不加任何自定义 active 样式（飞鹊 `.btn` 没有定义 `:active`，不自创）
- gallery-nav：全部用 opacity 变化

### 10.7 出页面前统一性自查清单（每次必查，不等提醒）

| 检查项 | 正确状态 | 常见错误 |
|--------|---------|---------|
| **投影** | 同层级卡片全有或全无 | 一张有 shadow-1 一张没有 |
| **装饰线/色块** | 只保留传达实际信息的 | section 标题前红竖线、激活态红横线 |
| **颜色种类** | 同组件状态不超过必要数量 | 3 种状态背景色 |
| **圆角** | 同类容器保持一致 | card 4px/8px 混用 |
| **hover 反馈** | 同类元素方式相同 | 有的有位移有的只改色 |
| **按钮层级** | 样式准确反映操作权重 | 用 secondary-dark 做主操作 |

## 八、响应式断点规范（做页面必读）

**做任何 MIC Web 页面前，必须读取完整规范文件：`飞鹊响应式规则-AI友好型规范.md`**

### 8.1 核心断点（基准 1440px）

| 断点 | 内容区 | Margin | Padding | 标题字号 | 卡片列 |
|------|--------|--------|---------|---------|--------|
| 1920 | 1440 | m(16)~xl(32) | m(16)~xl(32) | 32/36 | 6列 |
| 1366 | 1326 | m(16)~l(24) | m(16)~l(24) | 24/32 | 4列 |
| 1280 | 1240 | s(12)~l(24) | s(12)~l(24) | 22/24 | 4列 |
| 1024 | 984 | s(12)~m(16) | s(12)~m(16) | 18/22 | 3列 |
| 768 | 728 | s(12)~l(24) | s(12)~l(24) | 18/22 | 2列 |

正文 body=14px 全断点通用 · 中间态：≥1280 以大断点为主，<1280 以小断点为主

### 8.2 关键规则

- 特殊内容区：1840px（大图页）/ 1200px（展厅，兼容 4 个断点）
- 左右结构：1920→48:52 / 1280→50:50 / 768→100%堆叠
- 布局模式：拉伸 + 等比缩放 + 扩展 + 固定（混合布局）
- 简单页面可只做 1440/1280/1024 三个断点
- 页面 min-width: 768px · 圆角不随断点变化
